# 套餐创建与关联

Status: ready-for-agent

## Problem Statement

管理员在控制台里建不了套餐。「流量套餐」页面只能看，页面上那块虚线提示直说了：
后端只有 ListPlans 和 AssociatePlan，套餐得由人直接连进数据库、往 `traffic_plan`
表里 INSERT。

于是每次要一份新额度组合，流程就断在这里：管理员要么去找有库权限的人，要么自己
开一个数据库客户端，手写一条带 11 位字节数的 INSERT。结果是三件事——新套餐上线慢、
手写字节数容易差一个数量级、以及库权限被没必要地扩散给了只是想加个「季付 500G」
的人。

更靠后的一层：即便套餐建好了，管理员还得切回控制台、找到那个用户、再打开「关联
套餐」选一次。而「要一份新套餐」这件事，几乎总是因为**眼下有个具体用户需要它**。
两步之间隔着一次上下文切换，中间断掉就留下一份没人用的套餐。

还有一个已经在骗人的地方：套餐列表把**重置周期**当天数渲染，而后端存的是四选一的
枚举。一份季付套餐（枚举值 1）在页面上显示成「每 1 天」，一份月付套餐（枚举值 0）
显示成「不重置」。看着列表做决定的管理员，看到的是假的。

## Solution

管理员可以在控制台里直接建套餐，并且在建的同时就把它关联给需要它的用户——一次
操作、一个事务，不再有「建了但没关联」的中间态。

两个入口，同一个能力：

- **流量套餐页**新增一个「新增套餐」按钮。填名称、额度、重置周期，底部一个可选的
  「同时关联给用户」下拉。这是「我要往目录里加一项」的场景。
- **关联套餐对话框**里加一个内联的「新建套餐」。管理员正要给某个用户选套餐、发现
  下拉里没有合适的额度，就地建一份并自动选中。这是「我要给这个人一份额度」的场景，
  也是更常发生的那个。

额度按 GB 填，不再手写字节数。重置周期是四选一的下拉，页面上不再出现「每 1 天」
这种编造出来的说法——列表、新建表单、关联对话框三处共用同一套周期文案。

重名会被当场拒绝，因为关联对话框的下拉里两份同名套餐是无法分辨的，选错了事后从
用户身上也看不出来。

## User Stories

1. 作为管理员，我想在控制台里新建一份套餐，这样我不必为了加一条额度组合去申请数据库权限。
2. 作为管理员，我想在新建套餐时填套餐名称，这样它在关联对话框的下拉里能被认出来。
3. 作为管理员，我想按 GB 填写额度，这样我不用把 100G 心算成 11 位的字节数。
4. 作为管理员，我想在填完额度后立刻看到它将以什么形式展示，这样我能当场发现自己少打了一个零。
5. 作为管理员，我想从月 / 季 / 半年 / 年四项里选重置周期，这样我不会填进一个后端根本不认识的值。
6. 作为管理员，我想在新建套餐的同时把它关联给一个用户，这样我不必建完再切到另一个页面重做一次选择。
7. 作为管理员，我想在不指定用户的情况下只把套餐加进目录，这样我可以提前把常用额度备好。
8. 作为管理员，我想在「关联套餐」对话框里发现没有合适套餐时就地新建一份，这样我不用中断手上正在做的关联。
9. 作为管理员，我想让就地新建的套餐自动成为当前选中项，这样我不必在刷新后的下拉里再找一遍自己刚建的东西。
10. 作为管理员，我想让新建的套餐立刻出现在流量套餐列表里，这样我知道它真的进了目录。
11. 作为管理员，我想在套餐重名时被拦下来，这样目录里不会出现两条我自己都分不清的选项。
12. 作为管理员，我想在重名被拒时看到是哪个名字冲突了，这样我知道要改的是什么。
13. 作为管理员，我想在额度填成零或负数时被拦下来，这样我不会建出一份用户一上线就超量的套餐。
14. 作为管理员，我想在套餐名为空或只有空格时被拦下来，这样目录里不会出现一条没有名字的选项。
15. 作为管理员，我想让套餐名两端的空格被自动去掉，这样「月付」和「月付 」不会变成两份不同的套餐。
16. 作为管理员，我想在「同时关联」指向的用户不存在时，套餐也一并不要建出来，这样我重试一次不会多留下一份垃圾套餐。
17. 作为管理员，我想在创建失败时看到明确的失败原因，这样我知道该改哪一处再试。
18. 作为管理员，我想在创建成功时看到确认提示，这样我不会因为不确定而重复提交。
19. 作为管理员，我想在提交过程中看到按钮进入等待状态，这样我不会连点两下建出两份套餐。
20. 作为管理员，我想在套餐列表里看到真实的重置周期，这样我不会因为「每 1 天」这种假文案而误判一份季付套餐。
21. 作为管理员，我想让列表、新建表单、关联对话框里的周期说法完全一致，这样我不会怀疑它们说的是不是同一件事。
22. 作为管理员，我想在流量套餐页不再看到「套餐要去数据库里维护」这条提示，这样页面说的是它现在真的能做的事。
23. 作为管理员，我想知道套餐目前仍不支持修改和删除，这样我在命名和定额度时会更慎重一些。
24. 作为管理员，我想让「同时关联」沿用已有的关联语义，这样我不需要记住两套关于到期时间的规则。
25. 作为管理员，我想在关联发生时让用户的到期时间与流量重置时间一起被推到新周期末，这样两个标记不会互相打架。
26. 作为管理员，我想让「建的同时关联」对一个已有套餐的用户表现为覆盖，这样结果和我从关联对话框里改一次是一样的。
27. 作为普通用户，我想在管理员给我关联新套餐后立刻看到新的额度与到期时间，这样我知道我的账户已经生效。
28. 作为普通用户，我想让我的流量重置时间与套餐周期一致，这样我不会在周期中途莫名其妙被清零。
29. 作为非管理员的登录用户，我想让创建套餐这个动作对我不可用，这样我不能给自己发一份最大的额度。
30. 作为下一个读这段代码的人，我想在术语表里查到「额度」和「消耗」的区别，这样我不会被那条写着「消耗」的列注释带偏。
31. 作为下一个读这段代码的人，我想在术语表里读到「关联是覆盖不是续费」，这样我不会误以为重新关联会累加剩余时长。
32. 作为维护者，我想让周期与单位换算的规则有测试保护，这样以后有人改文案或改进制时会被测试拦住。
33. 作为维护者，我想让创建套餐的校验规则只存在于一处，这样它不会在请求标签和服务层之间慢慢漂移。

## Implementation Decisions

### 服务层

- 新增一个服务动作 **CreatePlan**，与既有的 ListPlans、AssociatePlan 并列，走同一个
  基于 Action 查询参数的分发入口，不新增路由。
- 仅管理员可调用，与同组的其他动作一致（服务层判定，不靠路由分组）。
- 请求承载四个字段：套餐名称、额度（**字节**，由前端换算后提交）、重置周期（枚举 0..3）、
  可选的用户 id。
- **可选用户 id 是「创建 + 关联」的全部机制**：给了就在同一事务里完成关联，没给就只
  往目录里加一项。前端不做「先创建、再调 AssociatePlan」的两步编排——那样第二步失败
  会留下一份没人用、也没人敢删的孤儿套餐，而套餐目录是所有管理员共享的下拉。仓库里
  已经为同形状的问题付过一次账：账号创建过去是先提交账号再关联套餐，关联失败就留下
  一个已经建好的账号，操作者重试便多出一个同名账号。
- 关联部分**复用既有的周期末计算**，不另写一份日期算术。账号创建当初把这段逻辑抽成
  导出函数正是为了让第二个调用方共用它，这里是第三个。
- 关联语义完全沿用 AssociatePlan：覆盖用户当前套餐，到期时间与流量重置时间一律从
  当下起算，不累加剩余时长。
- 事务边界包含查重、插入套餐、更新用户三步。用户不存在按「未找到」失败并整体回滚，
  套餐不落库。
- 返回**新建的套餐本体（含 id）**，而不是空响应：关联对话框的内联入口要用这个 id
  回填选中项。响应沿用列表接口里已有的套餐传输对象形状。

### 校验

- 校验规则集中在服务层的**一个纯函数**里，请求结构体上**不挂 `vd:` 校验标签**。这是
  对仓库现有习惯的一次有意偏离，两个理由：其一，`vd:` 只在 HTTP 绑定时生效，而这个
  仓库已经有绕开 HTTP 直接调服务层的先例（账号创建在自己的事务里内联调用套餐关联），
  规则挂在标签上等于那条路径完全没有校验；其二，标签规则不跑起完整请求就测不到，而
  周期边界和额度符号正是最该被表驱动测试盯住的部分。规则写两遍则必然漂移。
- 规则：名称去掉两端空格后不得为空；额度必须为正；重置周期必须落在枚举范围内。
- **重名拒绝**在事务内做查询判定，返回「冲突」类错误并带上冲突的名字。不加数据库唯一
  键：该表已有数据可能已经重复，加约束的迁移会直接失败。这与账号创建拦重复用户名的
  处理方式相同，理由也相同。

### 重置周期的枚举口径

- 周期是**枚举**（月 / 季 / 半年 / 年），不是天数。后端三处逻辑——周期末计算、到期
  重置调度、计费窗口判定——都建立在这个口径上，它是既定事实。
- 前端此前把周期当天数渲染，是错的，本次改为按枚举翻译。不做反向迁移：枚举值 0 在
  两套口径下含义相反（「月付」对「不重置」），迁移一旦写错就会静默地把所有月付套餐
  变成永不重置。
- **周期不提供「不重置 / 永久」选项**，空值不是一个合法的业务取值。空周期的实际效果
  不是「永久有效」而是完全脱管：周期末计算原样返回起点，到期时间等于创建时间；同时
  重置调度见到空周期直接跳过该用户，既不重置也不判超量。想表达「不限量」应当是一个
  明确的大额度，不是一个恰好绕过了调度器的空值。
- **枚举首项的值是 0**，因此请求结构体上的周期字段绝不能标记为「空值省略」——选「月付」
  时字段会被整个丢掉，落库成空，用户创建当场即处于已过期状态。这是本次改动里最容易
  悄无声息写错的一处。

### 前端

- 新增一个**套餐领域模块**，集中两件事：重置周期枚举与中文文案的映射、GB 与字节的
  双向换算。列表列、新建表单下拉、关联对话框三处共用同一份周期文案，坏掉的那份局部
  实现从页面组件里移除。
- 不放进既有的展示格式化模块：那个模块自述职责是「渲染后端送来的形状」，而 GB→字节
  是提交方向的输入换算，不属于展示。
- 这个模块与角色模块是同一个形状，并以它为先例：一小组固定的取值加上它们的中文文案，
  由前端自己知道，而不是从后端下发再照单渲染。重置周期正是这样的东西——四个取值，
  后端已有权威定义，文案是 UI 文案。
- 换算按 **1024 进制**。展示端的字节格式化就是 1024 进制的，输入端跟着走，管理员填 100
  才会在列表里看到「100.00 GB」；用 1000 进制会显示成 93.13 GB，第一个建套餐的人就会
  以为自己填错了。
- 流量套餐页：新增「新增套餐」按钮与对话框；对话框底部是可选的「同时关联给用户」下拉。
  页面上那块「套餐需要去数据库里维护」的虚线提示改写为「暂不支持修改与删除」。
- 关联套餐对话框：加入内联的「新建套餐」入口，成功后用响应里的 id 直接选中新套餐。
- 成功后需要让套餐列表与转发用户列表两处的缓存失效——带用户 id 的创建同时改动了这两
  份数据。

### 不做的模式

- 不加「先创建后关联」的两次请求编排。
- 不在账号创建表单里内联创建套餐。账号创建的事务已经在手工分配自增主键（加锁读最大
  id 再加一）并自行拦截重复用户名，是仓库里最脆的一段；再塞进一个可失败的创建，出错
  时「账号建了没有 / 套餐建了没有」会变成四种组合。
- 不动数据库结构，不加迁移。额度列那条写着「消耗」的错误注释保持原样：改它要动迁移
  并重跑实体生成器，而生成器会重写整个实体目录，diff 里会混进与本次无关的东西。这个
  错误改由术语表记录。

## Testing Decisions

好的测试只针对外部行为：给定一份请求，是被接受还是被拒绝、拒绝时是哪一类错误；给定
一个周期枚举值，渲染成哪句中文；给定一个 GB 数，换算成多少字节。不断言内部调用次序、
不断言私有状态。

接缝有两个——这个仓库跨两个运行时，最少只能是两个，一边一个。

**接缝一：服务层的纯校验函数。** 表驱动测试，与既有的周期末计算测试并排放在同一个测试
文件里（该文件已与被测代码同包，测不导出的函数没有障碍）。覆盖：名称为空、名称全是
空格、名称两端带空格被裁剪、额度为零、额度为负、周期低于下界、周期高于上界、周期取
每一个合法值。prior art 就是同文件里那组周期末计算的表驱动用例，包括它对空周期和越界
周期的处理方式。

**接缝二：前端。** 覆盖：四个周期枚举各自的文案、越界枚举值的兜底表现、GB 到字节的
1024 进制换算（含一位小数）、以及**新建套餐表单实际发出的请求体**——额度已换算成字节、
周期是枚举值（含「月付 = 0」不被丢掉）、带与不带用户 id 两种情形。

prior art 是账号表单的对话框测试：stub 掉 fetch、渲染整个对话框、断言发出去的请求体。
它存在的理由与这里完全相同——把一个容易悄悄退化的请求体形状钉死在测试里，而不是等它
在没人本地跑的数据库里出问题。纯换算函数的单元测试只能证明函数本身对，证明不了表单把
结果放进了请求；「月付 = 0 被序列化丢掉」这个最凶的坑，恰恰只在请求体那一层才看得见。
lib 层的模块测试仍然保留，覆盖文案映射与换算边界，prior art 是已有的错误处理模块测试
与 API 客户端测试。

周期字段的断言要落在「字段存在且等于 0」上，而不是「请求体包含预期的那些字段」。宽松的
对象匹配对一个被丢掉的字段照样通过——而字段被丢掉正是这里要防的那个失败。同理，值得
断言的不只是该发什么，还有不该发什么。

**不设接缝的部分：** 重名查重与事务本身。这两者只有真实数据库能验证，而本仓库目前一个
数据库测试都没有；为这一个动作引入测试夹具是另一件事的开头，不该夹在这次改动里做。
这部分靠手工验证：建一份重名套餐应被拒、带一个不存在的用户 id 创建应当既不留套餐也不
改用户。

## Out of Scope

- **修改套餐（UpdatePlan）**。不是加个接口就完事：额度被当作实时上限比对，改小额度会
  让所有已关联用户在下一轮调度里直接判定超量并触发周期滚动。这是一次跨用户的追溯性
  变更，语义要先定下来。
- **删除套餐（DeletePlan）**。用户的套餐 id 上没有外键，软删之后用户仍指着一个查不出来
  的 id，预加载拿到零值、周期为空，重置调度直接跳过该用户。结果不是「套餐没了」，而是
  **这个用户从此不限流量也不重置**，而且毫无提示。
- 账号创建表单里内联创建套餐。
- 「不重置 / 永久」周期。
- 周期口径从枚举改为天数的迁移。
- 额度列注释的修正迁移与实体重新生成。
- 用户端自助选购或查看套餐目录：套餐目录仍是管理端专属，普通用户从自己的套餐信息接口
  得知自己的额度。
- 数据库测试夹具。

## Further Notes

- 「关联」是覆盖不是续费，这一条在术语表里写死了。如果之后要做续费（从当前到期时间往
  后接，而不是从当下重算），那是一个新的动作，不是给这个动作加参数——两者对「用户当前
  还剩多少时间」的处理完全相反。
- 额度列的注释写着「消耗」，存的却是上限。本次不改注释，术语表里已经点名。任何第一次
  读这张表的人（包括后来的 agent）都会被它误导一次。
- 套餐名的唯一性只由服务层保证，数据库层面没有约束。若将来清理掉历史重复数据，可以再
  考虑补唯一键；在那之前，任何绕过服务层的写入都能制造重名。
- 本次改动前，一份季付套餐在列表里显示为「每 1 天」，月付显示为「不重置」。修复渲染
  之后，管理员看到的周期会与之前完全不同——这不是数据变了，是之前显示的是假的。上线
  时值得跟他们说一声。
